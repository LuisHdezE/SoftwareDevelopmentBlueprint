# Blueprint Factory — Development Constitution (proposal 1)

Status: PROPOSED. BF-OT-002. Baseline: consolidated agent proposal at 586cc2f2b629ced34519704924c0351310236ab4 (PR #75). This is a proposed overlay, not a stable Blueprint release, not an amendment of the frozen 0.5.5-dev candidate, and not automatic consumer adoption. Existing approved consumer contracts remain authoritative until explicit governed adoption. On adoption, this constitution supplements the adopted methodology; conflicts must be escalated and resolved explicitly before execution. No agent may override the adopted canonical methodology or approved project decisions.

## Mandatory principles

- BF-P01 — Clean Architecture is the default mandatory architecture for new development across applicable platforms: domain/application behavior independent from framework and infrastructure, inward dependencies, explicit boundaries/ports, testable use cases, adapters at the edges. Apply proportionately; no empty layers for ceremony. Alternative architecture requires explicit owner-approved exception. Existing Brownfield uses ALIGN, DO NOT REWRITE: inventory deviations and approved transition or exception, never silently rewrite.
- BF-P02 — Engineering good practices are mandatory: separation of concerns, SOLID where applicable, explicit contracts, maintainable names, consistent formatting, dependency hygiene, error handling, validation, reproducible builds, no secrets in code, appropriate automated checks. Exceptions to specific practices require scope, rationale and owner approval; no blanket quality waiver.
- BF-P03 — Architecture approval is individual and explicit. Architect presents a versioned exhaustive catalog of decisions, options, recommendation, compatibility, tradeoffs and consequences; owner chooses each applicable item or explicitly approves justified N/A. No silent defaults or bulk inferred approval. Approved choices include languages, framework versions, data authority, database, API, frontend, admin, mobile/desktop, security, deployment, QA, SEO/AI discovery and operational concerns. No implementation of a new project or affected architecture scope before applicable approvals. Discovery and non-production feasibility work may be separately authorized and must not certify implementation. Changes reopen affected decisions and invalidate dependent evidence proportionately. BF-OT-003/004 will define executable catalog and ledger; until then the constitution is not an implemented approval gate.
- BF-P04 — Reuse First: search pinned compatible WebBlueprint, ApiBlueprint, master skills and verified patterns before building; document reuse/adapt/new and rationale. No stack imposed by an existing composer; no copying private domain data or unnecessary dependencies.
- BF-P05 — API Contract First when API applies: early endpoint inventory with stable operationId, requirement, authorization and behavior; canonical OpenAPI before API implementation; no fake API for local/static/provider-only products. Backend owns implementation and contract deliverables; approved consumer bindings follow API gate. Version contract changes and revalidate impact.
- BF-P06 — Postman operational QA is mandatory for HTTP API scope governed by ApiBlueprint/master contract: importable collection and non-secret environment templates, coverage by operationId, positive/negative/authorization/business assertions, chained flows when applicable, deterministic isolated fixtures and cleanup, pinned runner and sanitized reports. No destructive tests against production. OpenAPI stays canonical. No required operation may be silently absent.
- BF-P07 — QA mandatory for every governed delivery, scope-based and independent from implementation acceptance. Real rendered browser execution for applicable web changes, including functional flows, responsive/accessibility and runtime errors; mobile/desktop execution for affected targets as applicable. Automated unit/integration/contract/regression and architecture conformance as applicable. Block missing execution; CI/build alone is not acceptance. Preserve distinct platform/slice evidence and human visual acceptance. Documentation-only scope requires relevant validation, not invented browser tests.
- BF-P08 — Security by design: threat/risk assessment proportionate to scope, server-side authority for API-backed systems, least privilege, tenant isolation, validation, secret handling, audit and data privacy as applicable. Blocking security findings cannot be bypassed by agent or schedule. Explicit owner risk decisions cannot falsify evidence or bypass legal/security boundaries.
- BF-P09 — Public discoverability mandatory when PUBLIC_INDEXABLE exists. Reuse specialist:search-ai-discoverability; SEO/GEO/AEO, crawl/index policy, structured data, AI search versus training permissions, and independent QA. No guaranteed ranking/citation; robots/noindex is not access control.
- BF-P10 — Evidence before PASS: exact candidate/revision, applicable criteria, reproducible commands/results, environment and source provenance; stale/missing/blocked evidence never PASS. Distinguish test fixtures from real execution and simulated role review from independent runtime. Preserve evidence-plane separation.
- BF-P11 — Orchestrator coordinates minimum honest role set and enforces stop conditions; Analyst/Planner/Architect and implementers retain boundaries. QA and Auditor independently review; no implementer final self-certification; no agent human approval. Explicit human authorization for governed merge, production deploy, release/tag and consumer adoption as required by adopted contracts.
- BF-P12 — Persistent governed learning: capture candidate lesson, source evidence, applicability, limitations, review and version. Documentation steward and relevant specialist propose; owner-approved normative changes only, no model retraining claim, no secrets or private consumer data in shared library. No automatic upgrades.
- BF-P13 — Portable execution: canonical version-pinned agents and skills, project-owned state, thin adapters for ChatGPT/Claude Code/Antigravity; disclose actual runtime capabilities and independence. No claim of native invocation or autonomous parallel execution unless verified.
- BF-P14 — Documentation, traceability and change control mandatory: source-controlled requirements, decisions, contracts, test evidence, delivery status, versions and relevant operational docs. Keep approved artifacts synchronized, never silently invent or amend product truth.

## Exception and escalation

Exceptions are explicit, narrow, versioned, time/scope bounded, with affected policy/decision IDs, requested alternative, rationale, risk, mitigations, owner identity and approval evidence, review trigger and affected tests. Pending/rejected/expired exceptions block affected work. No exception may manufacture PASS, approve on behalf of human, erase traceability, permit secret leakage, bypass applicable mandatory QA or security boundaries, or weaken the existing adopted version unilaterally. If a requirement is genuinely inapplicable, document the justification and obtain owner confirmation when architectural; N/A is not a waiver. Changes to scope/version invalidate affected exceptions and approvals until reviewed. No emergency implementation bypass is implied.

## Responsibilities and enforcement roadmap

Orchestrator enforces readiness; Architect owns interview and conformance plan; Analyst/Planner trace approved requirements; Database/Backend/Frontend implement approved boundaries; QA verifies execution; Security verifies applicable risk; Documentation maintains records and lessons; Auditor independently reviews evidence; owner decides. Existing eleven core roles and conditional specialist remain unchanged. Additional roles need a gap analysis. Existing gates are extended rather than replaced, notably architecture_ready, api_contract_ready, postman_ready, api_qa_pass, integration_qa_pass and discoverability_ready (proposal). BF-OT-003/004 will materialize decision catalog/approval validator; BF-OT-005–009 will wire roles and gates; BF-OT-010 learning; BF-OT-011–013 adapters. Until then this document is a policy proposal, not proof that all runtime enforcement exists.
