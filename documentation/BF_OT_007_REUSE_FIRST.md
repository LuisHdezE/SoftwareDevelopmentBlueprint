# BF-OT-007 — Reuse First integration proposal

Status: PROPOSED. Depends on PR #80. No stable release, automatic reuse, generator mutation or consumer adoption.

Pinned sources: WebBlueprint 6154927bbbad37ddb5372351a1298920c876128d; ApiBlueprint b9e4ff6d702e6a0e7a136d76be86691cbb30b214. Source profiles describe candidate full-export compatibility, not all reusable patterns. Architect and implementation roles must review both sources for bounded scope and record REUSE, ADAPT, NEW, BLOCKED or NOT_APPLICABLE with rationale. Independent review confirms real applicability, versions, license, selected components and evidence. Other reusable skills/patterns may be considered without claiming this export profile is compatible.

Use `python scripts/validate-reuse-assessment.py --ledger architecture-approval.json --record reuse-assessment.json`. The record contains repository, canonical ledger_digest, scope, and one ordered assessment per source. Each assessment contains id, commit, decision, rationale, components, review_evidence, requested_manifest, resolved_manifest, changes. For REUSE/ADAPT, supply nonempty selected component identifiers and actual requested/resolved manifest snapshots; changes lists every changed top-level field with field, evidence, status DECLARED_REVIEWED. For NEW/NOT_APPLICABLE, no export intent (empty lists/maps). BLOCKED always blocks. Review evidence is a declaration, not authenticated approval. Exit zero means READY_FOR_HUMAN_REUSE_REVIEW only, never permission to export or execute.

WebBlueprint ADR 0008 supports contract-first previews with replaceable mock providers. Treat mock contracts as design inputs only; canonical consumer OpenAPI and API gate govern real API-backed behavior. Selection = preview = export; no extra navigable modules. Browser QA and exported build evidence required at applicable consumer gates.

ApiBlueprint manifest v0.3 resolves endpoint dependencies and governance adjustments, including Sanctum and audit. Every changed field needs review; inspect individual nested additions and re-open affected ARC decisions if needed. Never trust client-supplied route details, assume generated stubs are implemented domain behavior, or certify a consumer API from generator QA. Reconcile OpenAPI, routes, operationIds and Postman at BF-OT-008.

The validator checks structural compatibility against declared selections, pins, ledger integrity and top-level manifest differences. It does not validate native manifest schemas, fetch or authenticate actual generator outputs, prove review authenticity, inspect nested change semantics, verify exact dependency versions, or certify runtime behavior. Synthetic fixtures are not exports. Actual generator execution and native manifest adapters require later integration/pilot; no automatic approval or bypass. No modification of either generator repository.
