# Self-Hosted GitHub Actions Runner Bootstrap

## Purpose

This runbook bootstraps a zero-GitHub-hosted-minute Linux/x64 runner for a private Blueprint repository.

Recommended host for the current operator environment:

`Windows 11 -> WSL2 -> Ubuntu 24.04 -> GitHub Actions self-hosted runner`

The runner is CI infrastructure. Installing Docker Engine on this host does **not** change a consumer project's `capabilities.docker` declaration.

## 1. Security model

Use one **repository-scoped** runner instance per private repository.

For the initial Blueprint Master bootstrap:

- repository: `LuisHdezE/SoftwareDevelopmentBlueprint`
- custom label: `blueprint`
- expected selector: `[self-hosted, linux, x64, blueprint]`
- trusted code only
- fork PRs denied
- no repository secrets stored persistently on the host

When CUSA-Digital later adopts stable 0.5.2, register a second runner instance in a different directory for that repository. Do not reuse one repository-scoped registration token across repositories.

## 2. Enable systemd in WSL2

In Ubuntu:

```bash
sudo tee /etc/wsl.conf >/dev/null <<'EOF'
[boot]
systemd=true
EOF
```

Then from Windows PowerShell:

```powershell
wsl --shutdown
```

Open Ubuntu again and verify:

```bash
systemctl is-system-running || true
```

`running` or `degraded` is acceptable in WSL when the required services are available.

## 3. Install base host dependencies

```bash
sudo apt-get update
sudo apt-get install -y \
  ca-certificates \
  curl \
  git \
  jq \
  tar \
  unzip \
  gzip \
  gnupg \
  lsb-release
```

Verify:

```bash
git --version
curl --version
tar --version
uname -a
```

## 4. Install Docker Engine for Actions service containers

The Blueprint Master validators do not need Docker, but the planned CUSA self-hosted profile uses GitHub Actions `services:` for MySQL. Installing Docker Engine now prepares the host for that later consumer without making Docker an application requirement.

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

. /etc/os-release
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu ${UBUNTU_CODENAME:-$VERSION_CODENAME} stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list >/dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker "$USER"
```

Close and reopen the Ubuntu shell so the group membership is refreshed.

Verify:

```bash
docker version
docker run --rm hello-world
```

The runner service account must be able to invoke `docker` without storing a sudo password in CI.

## 5. Create the Blueprint runner directory

```bash
mkdir -p ~/actions-runners/blueprint-master
cd ~/actions-runners/blueprint-master
```

In GitHub open:

`LuisHdezE/SoftwareDevelopmentBlueprint -> Settings -> Actions -> Runners -> New self-hosted runner`

Choose:

- Linux
- x64

GitHub will generate the current download URL, checksum and short-lived registration token. Run the generated download/extract commands exactly as shown by GitHub.

Do **not** paste the registration token into chat, source control, shell profiles or documentation.

## 6. Configure the runner

From the extracted runner directory use the command generated by GitHub, adding the custom Blueprint label when prompted or with `--labels blueprint`.

Equivalent shape:

```bash
./config.sh \
  --url https://github.com/LuisHdezE/SoftwareDevelopmentBlueprint \
  --token '<EPHEMERAL_TOKEN_FROM_GITHUB>' \
  --name blueprint-master-wsl \
  --labels blueprint \
  --work _work
```

Accept the default runner group unless GitHub offers a more restrictive repository-scoped option.

The default GitHub labels provide `self-hosted`, `Linux` and `X64`; the custom label adds `blueprint`.

## 7. Install and start as a service

From the runner directory:

```bash
sudo ./svc.sh install "$USER"
sudo ./svc.sh start
sudo ./svc.sh status
```

The GitHub repository Runners page should show the runner as **Idle**.

## 8. Verify the selector

The Blueprint development workflows use:

```yaml
runs-on: [self-hosted, linux, x64, blueprint]
```

If a workflow stays queued, verify that the runner page shows all four effective labels:

- `self-hosted`
- `linux`
- `x64`
- `blueprint`

Label matching is the dispatch contract. Do not weaken the workflow selector merely to make a misconfigured runner pick up jobs.

## 9. Operational hygiene

For a persistent runner:

- keep WSL and the runner updated;
- do not use the machine for untrusted fork PRs;
- do not store GitHub tokens or application secrets in the checkout;
- allow GitHub Actions to inject secrets only for the duration of a job;
- keep free disk space under observation;
- periodically inspect `_work` and Docker resources;
- do not run multiple CUSA runner instances on the same host unless port/service concurrency has been designed explicitly.

One runner instance processes one job at a time, which is acceptable for the current zero-cost private-repository strategy.
